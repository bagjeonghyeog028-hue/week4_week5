# 디버깅 전체 과정 요약

## 1. 문제 인식 및 재현
- **증상 명확히 정의**: "무엇이 기대와 다르게 동작하는가?" (기대 결과 vs 실제 결과)
- **재현 조건 확보**: 항상 발생하는지, 특정 입력·환경·타이밍에서만 발생하는지 파악
- **최소 재현 케이스 만들기**: 문제와 무관한 코드를 걷어내 가장 단순한 형태로 줄이기

## 2. 정보 수집
- 에러 메시지와 **스택 트레이스** 꼼꼼히 읽기 (가장 먼저, 가장 중요)
- 로그 확인, 최근 변경 사항(git diff, 배포 이력) 확인
- 환경 정보 점검: 버전, 설정, 의존성, OS, 데이터 상태

## 3. 가설 수립
- "어디서, 왜 틀어졌을까?"에 대해 **구체적이고 검증 가능한 가설** 세우기
- 가능성이 높거나 확인 비용이 낮은 것부터 우선순위 정하기
- 흔한 원인 체크: null/undefined, 오프바이원, 타입 불일치, 비동기 타이밍, 잘못된 가정, 설정 오류

## 4. 원인 좁히기 (격리)
- **이진 탐색**: 코드 절반씩 주석 처리하거나 중간 지점 값을 확인해 범위 축소
- `git bisect`: 어느 커밋부터 문제가 생겼는지 자동 탐색
- 입력값·환경·의존성을 하나씩 바꿔가며 **변수 하나씩만** 통제

## 5. 도구 활용
| 방법 | 용도 |
|---|---|
| print/로그 출력 | 빠른 값 확인, 실행 흐름 추적 |
| 디버거(중단점, 스텝 실행) | 변수 상태·호출 스택 실시간 관찰 |
| 단위 테스트 작성 | 버그를 코드로 고정, 재발 방지 |
| 프로파일러/네트워크 도구 | 성능·통신 문제 분석 |
| 러버덕 디버깅 | 코드를 소리 내어 설명하다 발견 |

## 6. 수정
- **근본 원인**을 고치기 (증상만 가리는 임시방편 지양)
- 수정은 작게, 한 번에 하나씩
- 수정 이유를 이해하고 있는지 확인

## 7. 검증
- 원래 재현 케이스가 해결됐는지 확인
- **회귀 테스트**: 다른 기능이 깨지지 않았는지 점검
- 관련된 엣지 케이스도 함께 테스트

## 8. 재발 방지 및 기록
- 버그를 잡는 테스트 케이스 추가
- 원인과 해결 과정을 커밋 메시지·문서에 기록
- 같은 유형의 버그를 막을 수 있는 구조적 개선(타입 체크, 린트, 입력 검증 등) 검토

# 빈칸 채우기형 디버깅 문제: 우선순위와 효율적인 접근법

코드 일부(한 줄, 한 문장, 한 조건식 등)를 채워 넣어 완성하는 유형이라고 보고 정리한 내용입니다.

## 1. 가장 먼저 볼 것 (우선순위)

**① 문제 설명과 요구사항**
- 입력/출력 형식, 제약 조건, 예제 입출력을 먼저 확인
- "이 코드가 최종적으로 무엇을 해야 하는가?"를 한 문장으로 정리

**② 빈칸 바로 앞뒤 코드**
- 빈칸 **위**에서 어떤 변수가 만들어졌고 어떤 값을 갖는지
- 빈칸 **아래**에서 그 값을 어떻게 사용하는지 (반환값, 조건, 인덱스 등)
- 빈칸은 결국 위에서 만든 재료를 아래에서 쓸 수 있는 형태로 이어주는 다리 역할인 경우가 대부분

**③ 빈칸의 자리(문법적 위치)**
- 조건식인가, 대입문인가, 반환문인가, 반복 범위인가?
- 자리가 정해주는 **타입**을 확인 (bool, int, list 등)

## 2. 효율적으로 보는 방법

**전체 흐름 → 빈칸 주변 → 세부 검증 순서로 보세요.**

1. **한 번에 훑기**: 처음부터 세세하게 읽지 말고 함수 구조, 반복문, 조건문 뼈대부터 파악
2. **예제 하나로 손 트레이싱**: 예제 입력을 넣고 빈칸 직전까지 변수 값이 어떻게 변하는지 종이나 메모에 적어보기
3. **빈칸에 들어가야 할 값 먼저 추론**: 문장을 쓰기 전에 "이 시점에 이 변수는 얼마여야 하지?"를 먼저 정함
4. **후보 문장 작성 후 재대입**: 채운 문장을 넣고 예제를 다시 돌려 결과가 맞는지 확인
5. **엣지 케이스 점검**: 빈 입력, 최솟값/최댓값, 0, 음수, 중복, 경계값(`<` vs `<=`)

## 3. 빈칸 문제에서 자주 나오는 오류 포인트

| 유형 | 확인할 것 |
|---|---|
| 경계 조건 | `<` vs `<=`, `range(n)` vs `range(n+1)`, 인덱스 0부터/1부터 |
| 초기값 | 합은 0, 곱은 1, 최솟값은 아주 큰 값, 최댓값은 아주 작은 값 |
| 갱신 위치 | 변수 업데이트가 반복문 안/밖 어디에 있어야 하는지 |
| 반환/출력 | return 위치, 반환 타입, 출력 형식(공백, 줄바꿈) |
| 타입 | 정수 나눗셈(`//`) vs 실수 나눗셈(`/`), 문자열↔숫자 변환 |
| 변수명 | 비슷한 이름의 변수 혼동 (`i`/`j`, `idx`/`index`) |

## 4. 시간 절약 팁

- **주변 코드의 스타일을 따라 쓰기**: 이미 쓰인 변수명, 자료구조, 패턴을 재활용하면 정답과 가까워짐
- **잘못된 부분이 아니라 "빠진 부분"에 집중**: 나머지 코드는 이미 맞다고 가정하고 빈칸만 논리적으로 해결
- **막히면 반대로 생각**: 빈칸 아래 코드가 요구하는 조건을 역으로 추적
- **비슷한 선택지가 있다면** 예제로 하나씩 대입해 소거

## 5. 한 줄 요약

> **요구사항 파악 → 빈칸 앞뒤 변수 흐름 추적 → 예제로 손 트레이싱 → 채운 뒤 재검증(경계값 포함)**



1. 먼저 알아야 할 기초 개념 (이것만 알아도 절반)

포인터는 "주소가 적힌 쪽지"예요.
Widget *w는 위젯 자체가 아니라 위젯이 있는 곳의 주소만 적힌 쪽지예요. 쪽지를 여러 장 복사할 수 있어요(items[2], w, self 등).

malloc / free는 "방 빌리기 / 반납하기"예요.

malloc: 힙이라는 큰 창고에서 방 하나를 빌려요.
free: 방을 반납해요. 그런데 쪽지(포인터)의 주소는 안 지워져요. 반납한 방의 주소가 쪽지에 그대로 남아 있는 게 문제의 출발점이에요.

NULL은 "이 쪽지는 아무 데도 안 가리킴"이라는 표시예요.
그래서 free(p); p = NULL;을 세트로 쓰는 거예요. 반납한 뒤 쪽지에 "무효"라고 적어두는 거죠.

2. 이번 문제의 버그 이름들 (자주 나오는 것만)
이름	쉬운 설명	이번 문제
Use After Free (UAF)	반납한 방에 다시 들어감	다이얼로그를 free했는데 render가 또 접근
Double Free	이미 반납한 방을 또 반납	핸들러 free + 정리 루프 free
NULL 역참조	무효 쪽지를 따라감	NULL 슬롯을 검사 없이 사용
Buffer Overflow	방보다 큰 짐을 넣음	(다음 문제에서 나올 수 있어요)
Memory Leak	방을 빌리고 반납 안 함	free 누락

디버깅 문제는 대부분 이 5가지 안에서 나와요. 다음 문제를 만나면 "이 중 뭐지?"부터 생각하세요.
